01

它是做什么的

官网标语："Highlight anything. Say what you think. It all stays." 产品由两部分组成——一个只在三家 AI 聊天站点注入的 Chrome 扩展，和一个集中管理所有标记内容的 Web 应用（library）。 私有 Beta，邀请制（jdong@wispal.ai），看起来是 1–2 人的小团队。

四个名词，先对齐语言

名词是什么
wisp一条「高亮片段 + 你的批注」，带精确锚点，是产品的原子单位。支持语音批注（转写）或文字批注，可选 emoji 和高亮/下划线颜色。
note一篇 AI 生成的笔记（markdown，支持 KaTeX 公式与代码高亮），来源是「整段对话快照 + 相关 wisp 的选中内容和批注」。
recipe（配方）服务端下发的笔记生成角度卡片 {id, name, description, illustration_svg}。用户不写 prompt，选卡片即可。
anchor（锚点）让高亮在页面刷新、对话重渲染后仍能找回位置的数据结构——全插件最值钱的技术，见 机制③。

权限与站点（manifest 实测）

  • content script 只注入 chatgpt.com / claude.ai / gemini.google.com
  • 权限：storage offscreen（录音）identity（Google 登录）alarms unlimitedStorage scripting
  • 两个快捷键：Cmd+Shift+E 开关侧栏、Cmd+Shift+Y 进入框选
  • 最低 Chrome 123，MV3，最低权限思路（没要 <all_urls>）

隐私姿态（隐私政策 × 代码互证）

  • 高亮/笔记本地优先存 IndexedDB；开 Cloud Sync 才上云（美国区服务器）
  • 语音录音只存本地 Blob，7 天自动删除；转写时音频瞬时发给 AI 提供商，不落库
  • 生成笔记时对话快照瞬时使用、不存储；来源 URL 只存 origin+path（掐掉 query/fragment）
  • AI 提供商配置为「不用于训练、不留 prompt 日志」

聪明细节：推开式侧栏

侧栏不悬浮遮挡对话，而是把整个页面挤窄——对聊天类布局零遮挡：

/* 侧栏展开时注入 */
html { width: calc(100% - ${侧栏宽}px) !important;
       position: relative !important;
       overflow-x: hidden !important; }
html .w-screen { width: 100% !important; }  /* 修 Tailwind 全宽类 */

侧栏本体：Shadow DOM 隔离样式 + 可拖拽的边缘 resize 手柄 + 宽度持久化。

聪明细节：边缘函数预热

Edge Function 冷启动要几秒。它的解法是——开始录音的瞬间就发一个空预热请求：

// 录音一开始就发
invoke("transcribe-annotation", {}, {
  headers: { "x-wispal-warmup": "1" }
}).catch(() => {})

// 等用户说完话，函数正好是热的
04

数据模型与同步

两张核心表 + 一张会话表，Zod schema 前后端共用。同步是「本地优先 + 可选云同步」：写入永远先落 IndexedDB，云端用三个经典机制保证一致性。

wisp —— 高亮批注记录

background.js · Zod schema 还原
{
  id, user_id, conversation_id, platform,
  message_index,          // 第几条消息
  content_offset,         // 消息内字符偏移
  anchor,                 // 精确锚点 → 见机制③
  selected_content,       // [{role, content}] 数组 → 支持跨消息框选
  annotation,             // 批注：文字 或 语音转写结果
  annotation_type,        // "custom" 手写 | 服务端注入类型
  style: { highlight_color, underline_color },
  status, is_favorite,
  title_at_creation, source_url,   // 仅 origin+path
  mutated_at, server_mutated_at, deleted_at, // 同步三件套
}

note —— AI 生成的笔记

{
  content, content_format: "markdown",
  origin: "ai",
  recipe: { id, name, description,
             illustration_svg },      // 用的哪个配方
  status: "note_generating" → "active" | "note_generation_failed",
  note_generation_error: { error_code, message, occurred_at },
  client_request_id            // 幂等键
}
// 另有 recipe_picker_sessions 表管理「选配方」会话：
//   recipe_generating → recipe_ready | recipe_generation_failed

幂等写入

每次写请求带 client_request_id（UUID），服务端遇重复返回 409 + existing_id，客户端复用已有记录——弱网重试不产生脏数据。

最后写入优先

每条记录有 mutated_at（客户端）与 server_mutated_at（服务端）双时间戳，upsert 时按时间戳决胜，多端编辑不丢更新方向。

软删除

删除只打 deleted_at 标记，同步按标记传播，永不物理删——多端最终一致，误删也可恢复。

05

五大核心机制

以下全部来自源码逐行分析。每个机制先讲怎么用，再讲怎么实现，标注关键参数。

机制 ① 划词浮动按钮selectionchange + caret rect

  • 监听 document 级 selectionchange（防抖 ≈150ms），校验：选区非折叠、起止点都能映射进消息容器
  • 按钮定位在选区最后一个光标矩形（caret rect）右侧，页面滚动 / resize 实时跟随重算
  • 流式输出中 → 按钮禁用（各平台适配器提供 isStreaming 检测），悬停提示，防止抓到半截回答
  • 拖拽选词期间有一个 session 在持续 tick，追踪"选区移动端"扫过的消息——因为长对话是虚拟列表，滚动时旧消息随时被卸载
  • 点击按钮 → session.finalize(boundary) → 产出 {selected_content, anchor, message_index, content_offset} → 弹批注卡

机制 ② 框选一段内容矩形 → 消息区间 · 全插件最重的工程

先破除误解：它不是截图、没有 OCR。框选的本质是几何 → 结构的映射：拖一个矩形，插件实时算出矩形与每条消息包围盒的交集，把「覆盖到的消息」整条捕获，Turndown 转成 markdown 存为一条 wisp（selected_content 是数组，所以天然支持跨多条消息框选）。下面这个模拟器还原了核心算法，进入框选模式后直接在消息上拖：

USER帮我用一句话解释：什么是文本锚点（text anchor）？
ASSISTANT文本锚点是一种把高亮/批注重新定位回原文的技术：不依赖行号或 XPath，而是记录选中文本本身和它的前后文指纹，页面结构变了也能找回位置。
ASSISTANT标准参照是 W3C 的 TextQuoteSelector：用 exact + prefix / suffix（前后文）三元组定位。WisPal 的做法本质上是它的消息级变体，按每条消息切分锚定域，抗平台重渲染。
USER那框选一整段对话是怎么办到的？
ASSISTANT框选不解析像素：拖拽矩形与消息包围盒求交，覆盖到的消息整条捕获。拖动过程中每 120ms 把扫过的消息容器 cloneNode 克隆暂存——虚拟列表滚动时 DOM 随时会被回收，先克隆才不丢内容。

            
真实实现里，这里会接：Turndown 转 markdown → 生成锚点 → 写本地 IndexedDB → 弹出语音/文字批注卡。

机制 ③ 锚点系统三级降级 · 全插件最值钱的技术

      

        
高亮要活过「页面刷新 + 平台重渲染 + 虚拟列表」。WisPal 的锚点 v2 schema 按消息级切分锚定域，每个 block 存：

        
锚点 v2 · schema_version: 2
{
  message_index,                // 第几条消息（会漂移，只是首选线索）
  role, platform_message_id,    // 平台原生消息 ID —— 最稳的消息定位键
  blocks: [{
    block_id,
    start_path, end_path,       // 消息容器内的相对 DOM 路径（不是全页 XPath）
    start_offset, end_offset,   // 字符偏移
    normalized_selected_text,   // 归一化后的选中文本
    text_offset_hint,           // 文本搜索的起始提示位
    prefix_context_hash,        // 前文指纹（不可逆哈希）
    suffix_context_hash         // 后文指纹
  }]
}

值得抄的工程细节

    
小团队但工程质量惊人，这些细节单独拿出来都值得进自己的 checklist。

    

      
边缘函数预热

框选/划词过程中持续 cloneNode(true) 暂存扫过的消息——DOM 随时会被平台回收，先克隆才不丢。

布局健全性自检
强制展开 content-visibility 后，求和各消息高度与 scrollHeight 比对，异常偏差记 warnOnce 诊断——自己给自己写监控。

      
幂等 + LWW + 软删
client_request_id 防重、双时间戳决胜、deleted_at 软删——本地优先产品同步层的标准答案，可直接照搬。

平台适配器抽象
三家站点各自实现同一套接口（消息容器/角色/ID/序数/流式检测/代码块预处理），新增平台 = 新增一个适配器类。

      
坦诚的失败路径
422"对话不可读"、402 积分不足、转写失败记录 last_error——每条失败路径都有明确的 UI 出口，没有静默失败。

      
最低权限姿态
只申请 3 个站点 host 权限，隐私页逐条对应代码行为；商店页还主动演示"本扩展无需读取该网站信息"的权限弹窗。

01

      
锚点技术值得直接搬

      
「消息级相对路径 + 归一化文本 + 上下文哈希」三级降级方案，比存 XPath 靠谱一个量级。NaYan 要做"跳回来源/关联会话片段"时照这个思路实现——桌面端不用面对虚拟列表，难度还会更低。

    

    
02

      
配方式笔记生成是好的产品形态

      
「全对话 + 用户批注 → 选配方卡片 → 服务端生成」。v3 的执行结果栏如果要加 AI 总结，用配方卡片而不是让用户写 prompt——WisPal 用 illustration_svg 把选择器做成了好看的卡片墙，这个交互值得像素级参考。

    

    
03

      
本地优先 + 幂等同步是上架标准答案

      
client_request_id 幂等 + 双时间戳 LWW + 软删除，和 NaYan 本地优先的形态完全兼容，将来上云同步可以直接按这套实现。

    

    
04

      
框选 = 映射到逻辑边界，不是抓像素

      
它把几何矩形映射到消息，NaYan 可以映射到命令步骤/会话条目——轻量、可编辑、可检索，比截图 OCR 高级得多。

    

    
05

      
差异化空间明确，付费信号积极

      
WisPal 只做 3 个网页、只做片段收藏，没有桌面端、没有项目/会话两级管理、没有执行过程记录——这正是 NaYan 的腹地。它私有 Beta + 积分付费墙，说明「留住 AI 对话价值」有人愿意付费，对你是好信号。
